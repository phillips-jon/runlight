# The Ruby port

`packages/ruby` is the `runlight` gem, which is the same library as the TypeScript SDK (`packages/sdk`) for Ruby, Rails, and Rack apps. It is a port, not a new design. The TypeScript SDK is the source of truth for every behaviour, answer, and stored byte, and when the two disagree, the Ruby side is wrong. The PHP port (`packages/php`) is the same port for PHP, already synchronous, and the Ruby files follow it file for file, so a later TypeScript change maps onto both.

## Rules

- Ruby 3.2 or newer, and Rails 7.2, 8.0, and 8.1. The one runtime dependency is `activerecord`, whose pools the store reads and writes through (on SQLite, Postgres, MySQL, or MariaDB, with the app's own driver gem: `sqlite3`, `pg`, `trilogy`, or `mysql2`). ActiveSupport brings `tzinfo`, which reports use for timezones. Rack is not a dependency. `Runlight::RackApp` speaks the Rack interface without it.
- `require "runlight"` autoloads every class on first use, from the table in `lib/runlight.rb`. In a Rails app it also loads `runlight/rails`, the engine.
- One TS module is one Ruby file at the mirrored path (`ua.ts` is `lib/runlight/ua.rb`, `Runlight::Ua`). The names that would clash with Ruby's own are renamed. `Runlight\Runlight` is `Runlight::Core` (and `Runlight.new` makes one), `time.ts` is `Runlight::Dates`, `hash.ts` is `Runlight::Hashing`, and the importers' HTTP helper is `Runlight::Importers::Client`. Free functions are `module_function` methods with the TS names in snake_case.
- No method takes the name of one every Ruby object or Kernel already has (`send`, `next`, `fail`, `system`, `open`, `hash`, `method`, `display`, `format`, `select`), since libraries, mocks, and serializers call those for their own purposes. Where the TS name is one of them the Ruby name says what it does instead. Mail transports `deliver`, SMTP reads `next_reply`, the sign-in throttle has `record_failure`, the assistant's prompt is `system_prompt`, and a timezone is read by `open_zone`. `Mmdb.open` stays, as a constructor in the manner of `File.open`.
- TS objects (SiteRow, Stats, Query, and the rest) are Hashes with the TS camelCase names as String keys, in the TS key order, never Structs. So the JSON they become is the TS JSON, and the store's rows are the TS rows.
- JSON is always written by `Runlight::Json`, which writes what `JSON.stringify` writes: numbers in JavaScript's form, slashes and Unicode as they are, and `Runlight::UNDEFINED` left out. `Runlight::Js` keeps the JavaScript string and number rules that answers depend on, such as lengths and slices counted in UTF-16 units, `trim`, `Number()`, `String()`, `Math.round`, and comparing text by UTF-16 code units.
- Public options are Ruby keywords in snake_case (`rate_limit:`, `base_path:`), read inside as the TS option names (`Runlight::Options`), so `"rateLimit" => 60` works too.
- Times are Integer epoch milliseconds, from the injected clock (`now:`), never `Time.now` in logic.
- TS's `fetch` is a fetcher, any object with `fetch(url, init)`. `Runlight::Http::NetFetcher` is the default, on Net::HTTP with redirects, a deadline on the whole request, a body cap, and resolve pins (a checked address is the one connected to). Every class that calls out takes the Core's fetcher, so tests replay requests without a network.
- What TS runs in the background runs in `Core#idle`, which the Rack app calls once the body is sent, or in `Core#check`, the scheduled check.
- No em or en dashes anywhere, as in the rest of the repo.

## Storage

`Runlight::Db::Database` is the little a store needs from a database (`dialect`, `all`, `run`, `affected`, `transaction`, `exclusive`) over an ActiveRecord connection class's pool. `Stores.active_record` uses the app's own (`ActiveRecord::Base`), and a store's writes join a transaction the app has open. `Stores.sqlite`, `Stores.postgres`, `Stores.mysql`, and `Stores.url` open pools of their own, each an abstract class under `Runlight::Db::Pools`, set up per connection as the TS drivers set theirs up. That means SQLite in WAL mode with a five second busy timeout, and Postgres with `statement_timeout` and an optional search path in libpq's `options`, so `RESET` comes back to them. MySQL and MariaDB get utf8mb4 with the server's own SQL mode and the statement timeout each names its own way. The SQL is the TS SQL for each dialect, with `?` placeholders filled in on the client as literals (as mysql2 fills them in for the TS driver), and on MySQL a "quoted" name in backticks and a backslash in 'text' doubled. The tables, columns, indexes, migrations, and stored formats are the TS ones, so one database can be served by the TS, PHP, and Ruby implementations at once. Creating tables takes a database-wide lock (an advisory lock on Postgres, `GET_LOCK` on MySQL).

## Rails and Rack

`Runlight::RackApp` answers in the order the standalone server does. A link domain comes first, then `/go/:slug` on the app's own domain, then the dashboard, the API, and the tracker under the base path. As middleware (`use Runlight::RackApp, runlight: RL`) it hands every other request to the app, after recording AI agent fetches (`observe`), and reads no request body the app will read. In Rails, the engine inserts the same middleware, configured by `Runlight.configure` in an initializer, so Runlight's requests never reach Rails' CSRF check or encrypted cookies. The install generator writes the initializer and a migration that runs the store's own migration (`disable_ddl_transaction!`, since Postgres builds indexes CONCURRENTLY). The engine's rake tasks are `runlight:check` and `runlight:migrate`.

The standalone server (`Runlight::Server::Standalone`, `exe/runlight serve`, `config.ru`) is the TS standalone server as a Rack app, configured from the same environment variables.

## Keeping the two in step

Behaviour lands in TypeScript first. `conformance/http.json` is then regenerated, and `rake test:conformance` replays all of it (every scenario and request) against `Runlight::Core` and its routes on SQLite, Postgres, MySQL, and MariaDB, comparing every status, header, and body. The unit tests read the language-neutral fixtures in `packages/php/tests/fixtures` and `conformance/` where they are. The assets in `assets/` (the dashboard, the tracker, locales, the world map, and `build.json` with the versions and hashes) are written by `scripts/ruby-assets.mts` from the SDK's generated files and checked by its `--check`.
