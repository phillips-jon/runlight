# The Java port

`packages/java` is a Maven build whose main artifact is `sh.runlight:runlight`, the same library as the TypeScript SDK (`packages/sdk`) for apps on the JVM. It is a port, not a new design. The TypeScript SDK is the source of truth for every behaviour, answer, and stored byte, and when the two disagree, the Java side is wrong. The PHP port (`packages/php`) is the same port for a synchronous language, and the Java files follow it file for file, so a later TypeScript change maps onto both. The build, the test setup, the adapters, and CI copy CronWatch's Java port, which Jon already approved.

## Artifacts

- `sh.runlight:runlight`, the core: the store over JDBC, the tracker endpoint, reports, goals, funnels, journeys, links, accounts with two-factor, OAuth, the MCP server, the assistant, mail, importers, connected installs, the routes, the adapter for the JDK's own HTTP server (`sh.runlight.server.JdkServer`), and the standalone server and its commands (`sh.runlight.server.Cli`, the jar's Main-Class). It has no compile or runtime dependencies at all, and the Maven Enforcer plugin fails the build if one appears. The app brings its JDBC driver.
- `sh.runlight:runlight-servlet`: the routes as a Jakarta Servlet 6 `HttpServlet`, and a `Filter` for short links, link domains, and AI agent fetches. `jakarta.servlet-api` is provided.
- `sh.runlight:runlight-spring-boot-starter`: auto-configuration for Spring Boot 3.5 and 4 with Spring MVC, from `runlight.*` properties, on the servlet module's classes. CI tests it on Boot 4 and on 3.5.0.

## Rules

- Java 21 or newer, tested on 21, 25, and 27 in CI, with javac's lint and Error Prone as errors and google-java-format checked by Spotless. The few Error Prone checks switched off are listed in the parent pom, each because the port keeps the TypeScript's shape.
- One TS module is one Java class at the mirrored package (`accounts/crypto.ts` is `sh.runlight.accounts.Crypto`, `importers/dub.ts` is `sh.runlight.importers.Dub`). Free functions are static methods with the TS names. `store.ts` is `sh.runlight.store.SqlStore` plus `Sql` for its free helpers. The core's two big classes, `Runlight` and `Routes`, take their options as `Runlight.Options` and `Routes.Options`, with setters named as the TS options are.
- TS objects (SiteRow, Stats, Query, and the rest) are `Map<String, Object>` (a `LinkedHashMap`, in the TS key order) with the TS camelCase keys, never records, so the JSON they become is the TS JSON and the store's rows are the TS rows. Values are `List<Object>`, `String`, `Long` or `Double` (`Js.num` makes a whole, safe number a `Long`), `Boolean`, `null`, and `Json.UNDEFINED` for a field to leave out.
- JSON is always written by `sh.runlight.Json`, which writes what `JSON.stringify` writes. `sh.runlight.Js` keeps the JavaScript rules that answers depend on: `trim`, `slice`, `Number()`, `String()`, `Math.round`, truthiness, and `decodeURIComponent`. Java strings are UTF-16, as JavaScript's are, so lengths and slices count as the SDK does. A lone surrogate stays in a string and becomes U+FFFD where JavaScript's would on its way out (`Js.utf8` for bytes, `Js.wellFormed` for the database).
- Regexes are written with `\z` for JavaScript's `$`, since Java's also matches before a final newline, and with `Js.SPACE` and `Js.DOT` for JavaScript's `\s` and `.`.
- Times are `long` epoch milliseconds from the injected clock (`Options.now`), never `System.currentTimeMillis()` in logic tests run on a fixed clock.
- Every outgoing request goes through a `sh.runlight.http.Fetcher`. The default, `JdkFetcher`, is HTTP/1.1 over sockets rather than `java.net.http.HttpClient`, because it must connect to the address `Safefetch` checked (resolve pins) while TLS still checks the certificate against the name and sends SNI. It keeps a deadline on the whole request and a cap on the body.
- Intl's region names and currency symbols come from `intl.json`, which `scripts/java-intl.mts` writes from Node's ICU, since 85 of the JDK's 3,380 region names differ. The assistant's model list sorts by a collation checked against Node's `localeCompare`. Scrypt is written in Java, since the JDK has none, and matches Node's bytes.
- One Runlight serves many threads. Its state is copied on write and read without locks, one visitor's requests take turns where TS queues them, and SQLite keeps one connection that threads take in turn. Postgres and MySQL keep a small pool of their own, or borrow from the app's `DataSource`.
- What TS runs after answering runs in `Runlight.idle()`, which each adapter calls once the answer is sent, or in `check()`. The tracker's rate limit, the link-domain list, site icons, and the assistant's hourly count are in memory, as in TS.
- No em or en dashes anywhere, as in the rest of the repo.

## Keeping the two in step

Behaviour lands in TypeScript first. `conformance/http.json` is then regenerated, and `ConformanceTest` replays every scenario and request against `Runlight` and its routes on SQLite, Postgres, MySQL, and MariaDB, comparing every status, header, and body. The unit tests read the language-neutral fixtures in `packages/php/tests/fixtures` and `conformance/` where they are, and port the PHP tests case for case. The dashboard, the tracker, the locales, the world map, and `build.json` are written into the core's resources by `scripts/java-assets.mts` from the SDK's generated files, and CI runs its `--check` and `java-intl.mts --check`. Tests reach Postgres when `RUNLIGHT_TEST_PG` is set (a schema per test) and MySQL and MariaDB when `RUNLIGHT_TEST_MYSQL` is set (a database per test).
